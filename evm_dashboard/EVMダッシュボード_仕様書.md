# EVMダッシュボード 仕様書（PM認識合わせ用）

> 対象画面: **メンバー稼働実績 ＆ チケット進捗推移**
> 作成目的: 本システムが「やりたいこと」を整理し、現状の実装で実現できているかを分析し、PMのイメージと実装の認識を突き合わせるための仕様書。
> 特に **メンバー別進捗バー** の表示パターンを網羅的に記載する。

---

## 0. 用語

| 略語 | 正式 | 意味 | 本システムの単位 |
|---|---|---|---|
| PV | Planned Value | 出来高計画値（その日までに完了している“はず”の工数） | 人日 (8h=1人日) |
| EV | Earned Value | 出来高実績値（進捗率 × 予定工数） | 人日 |
| AC | Actual Cost | 実コスト（投入された実績工数） | 人日 |
| BAC | Budget At Completion | 完成時総予算（全チケットの予定工数合計） | 人日 |
| SV | Schedule Variance | スケジュール差異 = EV − PV（＋で前倒し、−で遅延） | 人日 |
| CV | Cost Variance | コスト差異 = EV − AC | 人日 |
| SPI | Schedule Performance Index | スケジュール効率 = EV ÷ PV（1.0で計画通り） | 比率 |
| CPI | Cost Performance Index | コスト効率 = EV ÷ AC（1.0で計画通り） | 比率 |
| EAC | Estimate At Completion | 完成時総コスト見込み = AC + (BAC−EV)/CPI | 人日 |
| RS | Risk Score | 後続タスクへの遅延延焼リスク（独自指標） | スコア |

## 1. 本システムが「やりたいこと」（要件の再構成）

PMからのヒアリング要件を、システムの責務に分解すると次の通り。

1. **Redmineを唯一の入力源とする**
   - チケット（予定工数・開始/期日・進捗率・担当者）と、ニュース（日報スレッド）コメント（`#107 50% 8.0h` 形式）を機械的に取り込む。
   - PMやメンバーはダッシュボード用に別途データ入力しない（Redmine運用の延長で完結）。

2. **EVMでプロジェクト全体の健全性を可視化する**
   - PV/EV/AC とそこから導かれる SPI/CPI、完了予測日(EAC) を日次で算出。

3. **「人別」に進捗と将来遅延見込みを出す**
   - メンバーごとに、担当タスクの進捗・実績稼働・**将来いつ終わりそうか**を一目で把握。
   - これは “全体集計” では潰れてしまう個人差（前倒し／遅延）を浮かび上がらせ、**メンバー個人のモチベーションコントロール**に使うための画面。

4. **「過去の実績」と「未来の予測」を同じ時間軸で並べる**
   - 6/1〜（基準日）までは実績、基準日以降は予測、というファンチャート的表現。

5. **遅延の“延焼リスク”を早期に警告する**
   - あるタスクの遅れが後続タスク（＝同じ人の次の作業）にどれだけ波及するかをスコア化して提示。

```

│           │  time_entries  │  ・EVM集計          │           │  issue_journals/news  │
└──────────┘                └───────────────────┘           └──────────────────────┘
                                       │ calculate_evm_from_db(date)
                                       ▼
                              ┌───────────────────┐  JSON
                              │ server.py          │ ─────────▶ /api/evm-data?date=YYYY-MM-DD
                              └───────────────────┘
                                       │

                  ┌──────────────────────────────────────────────┐

```

- **基準日(base_date)**: `?date=` で指定。指定日が休日の場合は直近過去の営業日に丸める。
- 営業日 = 月〜金（土日除外）。PV配分・予測日数はすべて営業日ベース。

## 3. EVM算出ロジック（バックエンド）

### 3.1 PV（計画値）
- チケットの予定工数を **開始日〜期日の営業日に均等配分**（`est ÷ 営業日数`）。
- **完了タスクの未来PV消算（重要）**: チケットが完了(100%)になった場合、完了日（ジャーナル優先、無ければ最終実績日、無ければ基準日）**以降の未来日のPVは0h**として扱い、累積PVに加算しない。
  - 一律の「N日でクランプ」はしない（過密／変則スケジュールで破綻するため）。
- メンバーPV・タスクPVは「基準日までの営業日」分のみ合計する（未来分は分母に入れない）。

### 3.2 EV（出来高）
- その日時点の進捗率（`issue_journals` の履歴から、当日以前で最新の値）× 予定工数。
- **計画開始日より前でも、その日に進捗履歴があれば正しい進捗率を返す**（前倒し着手を正しくEVに反映）。

### 3.3 AC（実コスト）
- `time_entries` を `spent_on` 単位・チケット単位で集計（基準日まで）。

### 3.4 指標
- `SPI = EV/PV`, `CPI = EV/AC`（PV=0かつEV=0なら1.0）。
- `ETC = (BAC−EV)/CPI`, `EAC = AC+ETC`, `VAC = BAC−EAC`。
- **完了予測日**: SPIをベロシティとして残営業日を引き伸ばし、営業日カレンダーで加算。

### 3.5 リスクスコア RS（独自指標 / アダプタで算出）
```
RS = |SV| × (1 + 後続タスクの総人日) × (1 − 生産性[SPI])
```
- 後続タスク = 同一メンバーで計画開始日が後のタスク群、その予定工数合計（人日）。
- 完了タスク（SPI=1.0固定）・前倒しタスク（SPI>1）は RS≤0 となり発火しない＝**遅延中タスクのみ**が対象。
- `RS > 1.0` で警告バッジ表示。

## 4. 画面レイアウト（縦アライメント）

すべての行で日付グリッド（72px幅セル＋4pxギャップ）の縦軸を100%一致させる。

```
┌────────────────────────────────────────────────────────────────┐
│ ① 共通カレンダー目盛り行   [メンバー/カレンダー] 6/01 6/02 … 6/10 …  │  ← 画面最上部・固定
├────────────────────────────────────────────────────────────────┤
│ ② メンバー帯（アコーディオン見出し）                                │
│    [アバター 氏名 SPI/CPI 総工数]  [ⓐ 統合全体バー ＋ 相対ラベル] ▼  │
│   ┌──────────────────────────────────────────────────────────┐ │
│   │ ③ 日別稼働実績セル行  [日別稼働実績 合計Xh] 8h 8h 予 予 …      │ │
│   ├──────────────────────────────────────────────────────────┤ │
│   │ ④ チケット行（カード＋計画/実績ガントバー） ×タスク数           │ │
│   └──────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────┘
```

- 左カラム幅 `TASK_COL_W = 248px` を全行で固定。日付セルは `padding-left:32px` で見出しガント開始位置を揃える。
- セルの種別: **実績**(基準日以前) / **TODAY**(基準日) / **予測**(基準日以降, 半透明)。
- 未提出マーク: 当日に稼働/進捗はあるが「提出」フラグが無い場合、セル右上に **オレンジドット**。

## 5. メンバー別「統合全体バー」仕様（ⓐ）★最重要

### 5.1 思想
- メンバーの**全タスク合算**を1本のバーで表す。
- **ベース基準線 = 6/1〜6/10**（全体計画期間）を必ず1本描画。
- その上に **EAC（生産性加味）ベースの完了予測** を半透明で重ね、
  - 遅延 → 6/10を右へ突き破る（赤の斜線ストライプ）
  - 前倒し → 6/10より**手前で終わる**（縮む）
- 右側に **完了予測日＋相対営業日ラベル**（例: `06/08完 (2日前倒し)`）。

### 5.2 完了予測日(forecastEnd)の決定ロジック

| 条件 | 予測日の出し方 |
|---|---|
| 全タスク完了 | そのメンバーの**実際の最終稼働/進捗日**＝実完了日 |
| 未完了あり | 残営業日(基準日→6/10) ÷ **SPI** を `Math.round` → 基準日からその営業日数後 |

- ベロシティは **SPI単体**（CPIは掛けない＝スケジュール予測のため）。
- 相対ラベルの“ズレ日数”は **6/10からの営業日差**（土日スキップ）。
  - 遅延: `(⌈slip⌉日遅れ)` / 前倒し: `(|⌊slip⌋|日前倒し)` / `slip≒0`: `(予定通り)`

### 5.3 描画状態（色・形）

| 状態 | 判定 | ベースバー | 予測オーバーレイ | 赤ストライプ | ラベル色 |
|---|---|---|---|---|---|
| 前倒し | slip < −0.05 | 6/1–6/10 グレー | **緑半透明・6/1〜予測日（短い）** | なし | 緑 |
| 予定通り | −0.05〜+0.05 | 6/1–6/10 グレー | 青半透明・6/1〜6/10（全幅） | なし | 青 |
| 遅延 | slip > +0.05 | 6/1–6/10 グレー | 青半透明・6/1〜6/10（全幅） | **6/10→予測日に斜線赤** | 赤 |

### 5.4 パターン別の見え方（ASCIIイメージ）

凡例: `█`=ベース(6/1-6/10) / `▓`=前倒し予測(緑) / `▒`=遅延突き抜け(赤斜線) / `|`=6/10ライン

**A. 前倒し（例: 佐藤 SPI1.50 → 06/08完）**
```
6/1                     6/8  6/10
▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░|          06/08完 (2日前倒し)   ← 緑が6/8で止まり、6/10手前で縮む
```

**B. 予定通り（例: 鈴木 6/4 SPI1.00 → 06/10完）**
```
6/1                          6/10
████████████████████████████|             06/10完 (予定通り)   ← 6/10ぴったり
```

**C. 遅延（例: 永瀬 6/1 SPI0.60 → 06/17完）**
```
6/1                          6/10      6/17
████████████████████████████|▒▒▒▒▒▒▒▒▒▒  06/17完 (5日遅れ)   ← 6/10から赤斜線が右へ突き抜け
```

**D. 全タスク完了（例: 全タスク100%）**
```
6/1            実完了日 6/10
████████████████|░░░░░░░|                 06/05完 など   ← 予測=実完了日
```

### 5.5 シミュレーション実測（6/1〜6/5・各メンバー）

| 基準日 | 佐藤(前倒) | 鈴木(通常) | 永瀬(遅延) | 田中(遅延) |

| 6/01 | 06/08完 (2日前倒し) | 06/08完 (2日前倒し) | 06/17完 (5日遅れ) | 06/25完 (11日遅れ) |
| 6/02 | 06/08完 (2日前倒し) | 06/08完 (2日前倒し) | **06/15完 (3日遅れ)** | 06/23完 (9日遅れ) |

| 6/04 | 06/08完 (2日前倒し) | 06/10完 (予定通り) | 06/10完 (予定通り) | 06/12完 (2日遅れ) |

## 6. チケット個別ガントバー仕様（④）

各チケット行は **上段=計画バー / 下段=実績バー** の2段。

### 6.1 計画バー（青）
- `plannedStart 〜 plannedEnd`（チケットの開始日〜期日）を青で描画。固定。

### 6.2 実績バー（緑・進捗連動グラデーション）
- **開始**: 最初に実績工数(time_entries)が付いた日（`first_actual_date`）。
- **右端（★こだわりポイント）**: 完了/未完了を問わず、そのチケットに紐づく **time_entries の最新実績日(MAX)** で停止。**計画期日には引っ張られない**。
- 緑の濃淡: バー幅に対し進捗率(EV)分まで濃い緑、残りは薄い緑。
- ラベル: 完了→`完了`(緑) / 未完了→`進捗 X%`。

### 6.3 未着手（実績なし）
- time_entriesが1件も無いチケットは実績バーを描かず、実績段に **「未着手」** とだけ表示。

### 6.4 カード内テキスト
- `予定: 〇〇h / 実績: 〇〇h`（実績は**そのチケット固有**の合計。未着手は必ず `0.0h`）。
- 進捗率バー（細い帯）＋ステータスバッジ（進行中/遅延/完了）。
- **RSバッジ**: `RS>1.0` のとき `🔴 将来影響度：高（レバレッジ〇倍）`。

### 6.5 ステータス判定
| 状態 | 条件 |
|---|---|
| 完了 | 進捗 100% |
| 遅延 | 完了でなく、`予測終端 > 期日+1列` |
| 進行中 | 上記以外 |

### 6.6 個別バーのパターン（ASCIIイメージ）
凡例: `═`計画(青) / `▰`実績・EV(濃緑) / `▱`実績・残(薄緑) / `·`空

**P1. 完了・計画通り（#104 鈴木, 6/1着手→6/2完）**
```
計画  ═══════·········    (6/1-6/3)
実績  ▰▰▰▰▰▰·········    完了        ← 右端は最終実績日6/2で停止（6/3まで伸びない）
```

**P2. 前倒し着手・進行中（#111 佐藤, 計画6/4だが6/3着手・基準6/3で30%）**
```
       6/3 6/4
計画  ····═══════         (6/4-6/10)
実績  ▰▱·········         進捗 30%    ← 計画(6/4)より左の6/3から実績が立ち上がる
```

**P3. 遅延・進行中（#106 田中, 計画6/1-6/2を超過, 基準6/3で60%）**
```
計画  ═══·············    (6/1-6/2)
実績  ▰▰▱▱···········    進捗 60%    🔴将来影響度：高（レバレッジ2.9倍）
```

**P4. 未着手（#108 基準6/1, #109/#110 基準6/4）**
```
計画  ···═══════         (6/4-6/10)
実績  未着手                          予定:40.0h / 実績:0.0h
```

**P5. 階段状フライング（#108 鈴木, 6/3=8h→6/4=16h→6/5=24h）**
```
基準6/3 実績 ▰·········
基準6/4 実績 ▰▰········
基準6/5 実績 ▰▰▰·······   ← 実績右端が日々1列ずつ伸びる
```

## 7. リスクスコア(RS)バッジ仕様

- 数式: `RS = |SV| × (1 + 後続タスク総人日) × (1 − SPI)`。
- 表示: `RS>1.0` のときカード内に赤バッジ `🔴 将来影響度：高（レバレッジ〇倍）`、ツールチップに内訳。
- 実測例（後続=5人日 / 完了・前倒しは非発火）:

| チケット | 基準日 | SV(人日) | SPI | RS | バッジ |

| #106 田中 | 6/01 | −0.9 | 0.40 | 3.24 | 🔴 3.2倍 |
| #106 田中 | 6/02 | −1.8 | 0.40 | 6.48 | 🔴 6.5倍 |

| #104 鈴木(完了) | 全日 | — | 1.00 | 0 | なし |

## 8. 「実現できているか」の分析（現状評価）

DockerのRedmine相手に `setup_simulation.py` をE2E実行し、6/1〜6/5を1日ずつ取り込んで検証した結果。

| 要件 | 実現状況 | 根拠 |
|---|---|---|
| RedmineのみでEVM自動算出 | ✅ 実現 | news正規表現取込→SQLite→集計が一気通貫 |
| 全体EVM可視化 | ✅ 実現 | project_summary に PV/EV/AC/SPI/CPI/EAC |
| 人別・進捗/将来遅延 | ✅ 実現 | member_stats＋統合全体バー＋予測日 |
| 過去実績/未来予測の同一軸 | ✅ 実現 | 実績/TODAY/予測の3種セル＋ファンチャート |
| 前倒し着手の正しい評価 | ✅ 実現 | 6/3 佐藤 SPI/CPI=**1.50維持**（1.00へ落ちない） |
| 完了タスク未来PV消算 | ✅ 実現 | 完了日以降PV=0で分母水増し解消 |
| 実績バー右端=最終実績日 | ✅ 実現 | 完了#104は6/2で停止（期日に伸びない） |
| 未着手の実績0h・誤マッピング | ✅ 実現 | チケット固有集計、完了マーカーも固有化 |
| 遅延延焼リスク(RS) | ✅ 実現 | RSバッジ（新規実装） |
| モチベーション用途 | ✅ 寄与 | 個人別の前倒し/遅延が明確に分離表示 |

### 8.1 認識合わせが必要な点（要確認）

1. **完了予測日の丸め**: 残営業日÷SPIを `Math.round`。
   - 6/02 永瀬「3日遅れ(6/15完)」は厳密一致。一方 **6/01 永瀬は数式上「5日遅れ(6/17完)」**（SPI0.60では `round(7/0.6)=12営業日`）。PMイメージの「4日遅れ」と1日差。
   - → 「6/01=4日遅れ」と「6/02=3日遅れ(6/15)」を**同時に満たす単一丸め規則は存在しない**ため、日付明示のある6/15側を優先。**切り上げ/四捨五入/切り捨てのどれを正とするか**をご判断ください。

2. **完了予測のベロシティはSPIのみ**（CPI非考慮）。「コスト効率も加味した完了予測が欲しい」場合は EAC連動に変更可能。

3. **“前倒し”ラベルは⌊slip⌋・“遅延”は⌈slip⌉**（前倒しは控えめ、遅延は厳しめに丸め）。意図通りか要確認。

4. **メンバー全タスク完了時の予測日**は、現状メンバー全体の最終“稼働日”を採用（チケット個別の完了マーカーはチケット固有に修正済だが、メンバー集計側は稼働日ベース）。完了日を厳密にしたい場合は調整余地あり。

5. **RSの「生産性」はタスクSPI**を採用。CPI（コスト生産性）や両者の合成にする選択肢もある。「レバレッジ〇倍」の数値はRS値そのものを表示している点も要確認。

### 8.2 留意（運用前提）
- 進捗・実績は **Redmineニュースの定型コメント**（`#<id> <pct>% <h>h`）に依存。書式逸脱は取り込まれない。
- 期日(due_date)未設定チケットはPV配分が不定になりやすい（要・期日入力運用）。
